# Deterministic STEP Content Identity in MechCAD — Normative Platform Spec (Proposed)

**Status:** proposed normative Spec, pending independent acceptance. This document is `DOCUMENTATION_ONLY`. It authorizes no implementation by itself while in proposed state. Implementation may proceed only after (1) this Spec is independently accepted, (2) an applicable implementation Plan/baseline is accepted as required by project process, and (3) the implementation task is explicitly authorized. A separate implementation Plan is required AFTER Spec acceptance; no Plan is created here.

**Scope:** deterministic semantic identity for STEP-sourced geometry, separated from exact raw artifact provenance. Planning/architecture only. No production code changed by this Spec. No historical MINI Rev3/Rev4 modified. No FreeCAD/Gmsh/CalculiX executed. No commit/push/reset/clean/stash/install.

**Trigger:** `MECHCAD_SOURCE_IDENTITY_CONTRACT_REQUIRES_PLATFORM_DECISION` / `PLATFORM_CAPABILITY_GAP_DETERMINISTIC_CONTENT_IDENTITY`.

## 1. Authority and non-goals

## 2. Normative identity definitions

**D1 — Raw artifact byte identity (frozen, authoritative for bytes):**

```text
raw_artifact_identity := "sha256:" + hex(sha256(raw_bytes_exact_as_stored))
```

Holds for `EngineeringArtifact.sha256`, `ImportedCadComponent.artifact_hash`, retained `GeometrySourceReference.artifact_hash` fields, and raw provenance tuples. Purposes: byte integrity, forensic provenance, tamper detection, exact artifact binding, restart verification. MUST NOT be replaced, normalized, or aliased to content identity. Verification recomputes over bytes read from `ArtifactStore`.

**D2 — Stable STEP content identity (new, separate):**

```text
step-content-identity@1 := "sha256:" + hex(sha256(canonical_identity_bytes_v1(original_step_bytes)))
```

Typed record `{algorithm: "step-content-identity@1", content_hash: "sha256:…"}`. Consumes original bytes; never mutates/replaces the stored artifact. Deterministic, versioned, fail-closed. Algorithm identifier is part of the binding; verifiers check value AND algorithm string.

**D3 — Dual binding:** a new trusted source is acceptable only when raw-layer acceptance AND semantic-layer acceptance both pass (see §20). Neither layer substitutes.

Raw stored STEP bytes MUST remain unchanged. Stable identity MUST NOT replace raw identity.

## 3. Semantic reference identity

Legacy `GeometrySourceReference.reference_hash` is a raw/provenance reference identity: its payload contains `artifact_id` + `artifact_hash` (operational provenance values) via `reference_hash_payload` / `candidate_geometry_reference_payload` (`models/geometry_identity.py`, `candidates/models.py:182-220`). It remains **frozen** for legacy schemas and stays byte/artifact oriented.

New schemas MUST introduce a separate explicitly versioned **semantic geometry reference identity** field `semantic_reference_hash` with payload exactly:

```text
{
  "source_identity": <str>,
  "format": "step",
  "coordinate_system_id": <str|null — included only under the M13 rule, i.e. present iff coordinate_system_id is not None>,
  "content_identity": "sha256:…",
  "content_identity_algorithm": "step-content-identity@1"
}
```

Hash = `sha256(canonical_json(payload))` with `sha256:` prefix. Raw `artifact_id`/`artifact_hash` remain present as sibling fields for provenance validation but MUST NOT enter this projection directly or transitively. Legacy `reference_hash` validators unchanged. Do NOT reuse one unversioned hash for both raw and semantic purposes.

## 4. artifact_id semantics

`artifact_id` is provenance/storage identity, NOT engineering semantic identity.

Two independently published STEP artifacts with different artifact IDs, different raw SHA due only to the permitted timestamp variation, and equal `step-content-identity@1` MUST be able to produce the SAME new semantic candidate identity. `artifact_id` remains mandatory for raw provenance/restart resolution (store lookup, byte rehash) but MUST NOT feed any new semantic hash projection (§6–§17).

## 5. source_binding semantic projection

`CandidateSourceBinding` fields (`candidates/models.py:114-127`) are classified as follows for the new chain:

| Field | Classification | In new semantic hash? |
|---|---|---|
| `project_id` | Canonical authority binding (authority namespace) | INCLUDED — identical values under different projects are different authorities |
| `source_revision` | Canonical-state binding (which snapshot) | EXCLUDED — validated separately via `validate_against` + currentness |
| `source_state_hash` | Canonical-state binding (opaque snapshot hash; commits to full revision bytes, a binding coordinate, not engineering content) | EXCLUDED — validated separately; DesignState authority is NOT weakened because `validate_against` still enforces exact revision/state match and `value_hash` recompute below still enforces consumed values |
| `consumed_authority[].path` | Engineering semantic input (which canonical path was consumed) | INCLUDED |
| `consumed_authority[].authority` | Engineering semantic input (under which authority kind) | INCLUDED |
| `consumed_authority[].value_hash` (legacy) | Canonical-state replay evidence (opaque w.r.t. raw geometry) | EXCLUDED from semantic hash — retained for `validate_against` replay/currentness ONLY (correction: the prior "INCLUDED as defined commitment" verdict is WITHDRAWN — defined-but-raw-dependent is not timestamp-invariant) |
| `consumed_authority[].semantic_authority_value_hash` (new) | Semantic value commitment (see Option-B rule below) | INCLUDED |

Semantic value rule — OPTION B chosen from production evidence (Option A rejected with cause): the accepted M13-4 chain consumes `/physical_mechanisms` (fixture: `m13_4_acceptance_fixtures.py:730-759` — `/id`, `/requirements`, `/constraints`, `/authoritative_parameters`, `/physical_mechanisms`), whose resolved values contain `CanonicalComponentSpecification.geometry_source` (raw artifact ID/SHA via `canonical_geometry_reference_payload`, `physical_mechanism.py:270-309`) and M13 subtrees with `GeometryArtifactIdentity` records. (Attribution corrected: M12-6's `_ALL_CONSUMED_PATHS` — `test_m12_revolute_drive_production.py:62-76` — consumes only scalar requirement/constraint/parameter/interface paths and does NOT include `/physical_mechanisms`; Option B remains justified by M13-4 alone.) Restricting new-family paths to raw-free values would therefore exclude a legitimately required authority path — Option A is incompatible with the accepted chain, so Option B is normatively required. New pure-function projection **`semantic_authority_value_hash(path, resolved_value, verified_semantic_geometry_bindings)`** is type-directed and context-bound. `verified_semantic_geometry_bindings` is a verifier-local, non-persisted map produced only after dual-binding each raw geometry source: resolve the artifact ID, verify the exact stored bytes against the bound raw SHA, recompute `step-content-identity@1` from those same bytes, and bind that semantic identity to the resolved geometry reference. Each lookup requires the exact raw binding tuple `{artifact_id, artifact_hash, source_identity, format, coordinate_system_id}`; missing or mismatched context fails closed, and no semantic value may be derived from an artifact ID or SHA alone. For `/physical_mechanisms`, first apply the explicit `canonical-physical-mechanism@4` projection from §11, including explicit `canonical-component-specification@4` projections and re-derived `@4` specification-hash linkages; do not recursively dump or selectively strip the resolved mechanism. Generic fallback rule (normative — replaces the undefined per-project allowlist; platform-neutral, no per-project field list): (1) `/physical_mechanisms` values project ONLY through the typed `canonical-physical-mechanism@4` and `canonical-component-specification@4` contracts (§§6A/11). (2) Any other resolved canonical DesignState value containing NO recognized raw-bearing geometry/provenance shape is preserved COMPLETE and unchanged — compute the semantic authority value hash over its full canonical JSON; no field is deleted by name and no per-project allowlist is invented. (3) Any other path/value containing a recognized raw-bearing geometry/provenance shape with no explicitly defined typed semantic projector FAILS CLOSED (unknown shape = reject, never hash through). (4) Geometry content identity comes ONLY from `verified_semantic_geometry_bindings`, never from artifact_id/raw SHA. For the §6A-covered shapes inside any value: transform `GeometryArtifactIdentity` through the §6A identity projection, explicit geometry-reference fields through §3, explicit geometry-source fields through §3, and each persisted M13 record through its named §6A subprojection. Self-hashes are omitted only by those explicit type projections; semantic linkage hashes are retained or re-derived only where their field is explicitly classified. No recursive key-name heuristic classifies hash fields. Any raw-bearing value or field outside the explicit allowlist fails closed (unknown shape = reject, never hash through). The walk is recursively finite (DesignState values are finite JSON trees; cycle impossible in canonical serialization). `semantic_source_binding_hash` payload consumes `{path, authority, semantic_authority_value_hash}` per consumed reference (document order preserved) — NEVER the legacy raw-dependent `value_hash`. The legacy binding object and legacy `value_hash` remain exact replay/currentness evidence validated against DesignState via `bound_to`/`validate_against`; DesignState canonical authority is NOT weakened (nothing is dropped from validation — the semantic layer is an additional commitment, and `validate_against` still enforces exact revision/state/value match). Restart verification recomputes BOTH the legacy `value_hash` chain (replay) and the semantic chain (identity) from the reloaded DesignState revision; either mismatch fails closed. Tested with a raw-only geometry change (timestamp/artifact-ID rotation under identical engineering values): legacy `value_hash` MAY differ while `semantic_authority_value_hash` — and therefore `semantic_source_binding_hash` — MUST stay same.

Legacy full-binding hash (`_hash(source_binding)` over all four field groups) remains frozen for legacy chains. New records carry the legacy binding object unchanged for validation AND a separate `semantic_source_binding_hash` field; downstream new hashes reference only the semantic one.

## 12B. Declared-field and derived-value completeness (normative)

Completeness = every DECLARED_MODEL_FIELD has exactly one classification (INCLUDED / EXCLUDED / TRANSFORMED); derived values are checked separately, each with an explicitly defined derivation, and are NEVER counted toward declared-field equality.

### 18A.1 Candidate-CAD per-slot verification order (normative amendment)

The candidate-CAD `@2` verifier MUST execute the following order. This is the
complete trusted candidate-CAD order and supersedes any abbreviated raw-domain
summary in the preceding `candidate-cad-provenance@2` paragraph. Trusted
mapping correspondence is always per-mapping and per-slot, never existence of

   authority, including the exact candidate physical-instance and authoritative
   component-specification relations.
2. Derive the complete verifier-local `required_raw_source_artifacts` set from
   that verified authority walk, including every required raw
   `(artifact_id, artifact_hash)` pair.
3. Require exact bidirectional envelope-to-required-set equality: no envelope
   raw artifact is extra and no required raw artifact is missing. Duplicate or
   conflicting artifact IDs fail closed.

   `required_trusted_raw_binding_by_slot[(physical_instance_id,
   cad_instance_id)]` from the authoritative component specification's single

   and its single imported component definition through `part_id`, as specified
   in §9A.
7. Require the expected raw pair from step 5 to equal the actual imported raw
   pair from step 6, and require that pair to be in the already verified
   complete required raw set. Missing or ambiguous resolution rejects.
8. Only after steps 1-7, recompute `step-content-identity@1` from those exact
   verified bytes for each correctly bound slot.

   semantic `geometry_definition_identities`, and trusted representation

## 22. STEP content grammar + bounded parser contract

Accepted volatile field: ONLY HEADER `FILE_NAME` second positional `time_stamp`. Timestamp grammar is exactly `YYYY-MM-DDTHH:MM:SS` (ASCII digits + literal `-`, `T`, `:` separators; 4-2-2-T-2-2-2 digit counts). No timezone, fractional seconds, whitespace variants, alternate date forms, or provider extensions in @1. Any deviation fails closed.

`step-content-identity@1` canonical token replacing the timestamp inner chars: `1970-01-01T00:00:00` (fixed length, documented arbitrary constant). All other bytes preserved.

Bounded envelope parser (sufficient for identity, NOT a full ISO 10303 validator): normative bounds — max input 134,217,728 bytes (128 MiB); max HEADER section 1,048,576 bytes (1 MiB); max parenthesis nesting depth 32; require exactly one `ISO-10303-21;` header stamp, exactly one `HEADER;..ENDSEC;`, exactly one `DATA;..ENDSEC;` in order; exactly one `FILE_NAME(` in HEADER; STEP STRING parsing with doubled-apostrophe `''` escape; unterminated string → reject; unbalanced parens → reject; multiple `FILE_NAME` → reject; bad timestamp → reject; non-ASCII in HEADER scope or non-UTF-8-decodable HEADER → reject; exceeding any bound → reject. Do NOT use broad whole-file regex replacement; replacement boundary is the single parsed timestamp token.

Whitelist stays narrow — explicitly NOT normalized: FILE_NAME file-name param, author, organization, preprocessor_version, originating_system, authorization, FILE_SCHEMA, all DATA, entity ordering, IDs, whitespace, line endings, paths, placements, units, tolerances. Any difference outside the accepted token changes identity or fails closed.
