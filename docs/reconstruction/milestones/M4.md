## Historical Role

M4 is the deterministic run-control and orchestration layer around the
already-existing M1-M3 boundaries:

```text
Canonical DesignState
    -> Run -> RunPlan -> Task DAG -> TaskExecutor protocol
    -> immutable result / optional Evidence
    -> M2 proposal application -> canonical revision advancement
    -> M3 invalidation -> task staleness / convergence
    -> CURRENT-Evidence completion gate
```

```text
M1 = canonical revision persistence
M2 = canonical mutation
M3 = derived invalidation / Evidence freshness
M4 = run lifecycle, scheduling, execution coordination, convergence,
     completion, and resume
```

M4 composes M1-M3; it does not reimplement their authority.

## Persistence

```text
projects/<project_id>/runs/<run_id>/
  manifest.json
  state.json
  plan.json
  tasks/<task_id>/definition.json
  tasks/<task_id>/state.json
  results/<result_id>.json
  events/EVT-000001.json
```

Directories are created lazily. Manifest, task definitions, results, and
events are immutable exclusive-write records. Run and task state use
temporary-file flush/fsync plus `os.replace()` atomic replacement. This is not
a multi-file transaction.

`plan.json` is a material deviation: `create_plan()` writes it with
`exclusive=False`, so it is overwriteable. `RunStore.write_plan()` is unused
and derives an incorrect project path from `run_id`.

## Run And Task Control

Run creation reads actual M1 current state. Initial and active revision/hash
begin equal, and callers cannot provide arbitrary creation bindings.
`RunManifest` preserves initial run/project identity, revision, hash, maximum
iterations, and creation timestamp; mutable state records active progress.

Run statuses are `CREATED`, `PLANNED`, `RUNNING`, `BLOCKED`, `FAILED`,
`COMPLETED`, and `CANCELLED`. Actual controller transitions are creation to
`CREATED`, planning to `PLANNED`, completion to `COMPLETED`, and convergence or
invalidation failure to `BLOCKED`. There is no centrally enforced transition
table, no controller path sets `RUNNING`, and terminal status does not
generally prevent later mutation.

```text
RUN_STATE_MACHINE: IMPLEMENTED_WITH_DEVIATIONS
```

`TaskDefinition` is immutable and includes task/run identity, task type,
objective, revision/hash binding, dependencies, required/produced engineering
nodes, and creation timestamp. Reruns require a new task identity.

M4 task-DAG nodes are task IDs and edges are execution prerequisites. M3
`DependencyGraph` nodes are engineering/Evidence nodes and edges are
invalidation propagation. They are separate graph systems.

`TaskScheduler` uses sorted Kahn ordering, rejects unknown dependencies and
cycles, and deterministically orders ties lexically. Duplicate task IDs can
collapse through dictionary construction and duplicate dependencies are not
explicitly rejected. A task is ready only if every prerequisite succeeded;
`SKIPPED` does not satisfy success, and `STALE` suppresses readiness without
automatically blocking downstream tasks.

## Execution And Evidence

```python
TaskExecutor.execute(
    task: TaskDefinition,
    context: TaskContext,
) -> TaskExecutionResult
```

`TaskContext` carries project/run identity, active revision/hash, and the
canonical `DesignState` at that revision. M4 contains no OpenCode, LLM, agent,
tool, CAD, FreeCAD, FEA, database, optimizer, parallel, distributed-worker, or
external-service runtime.

`validate_result()` checks exact task ID, bound revision, and bound state hash;
a mismatch raises `StaleTaskResultError`. Result files are immutable. M4 does
not independently verify that each Evidence object contained in a result has
matching task/result provenance before writing it through `EvidenceStore`.

```text
RESULT_EVIDENCE_BINDING: PARTIAL
```

Ready-task execution loads definitions/states, persists `RUNNING`, constructs
context, calls the executor, validates and writes the result, writes Evidence,
persists final task state, and emits an event. Evidence persistence can fail
after the immutable result is already written; the controller then attempts to
record task failure. No multi-record atomicity is claimed.

## Revision Advancement, Completion, And Resume

Historical `apply_approved_proposal()` calls M2 first, then records active
revision/hash, iteration, and history; persists run state and a
`REVISION_ADVANCED` event; then builds and records M3 invalidation and marks
relevant pending/ready tasks stale. This is the first retained production
orchestration path from `AppliedChangeResult` to M3 invalidation persistence.

If M3 invalidation persistence fails after M2 succeeds, canonical state is not
rolled back. The run follows the new canonical revision, retains advanced
iteration/history, becomes `BLOCKED`, emits `RUN_BLOCKED`, and does not guess
affected nodes.

```text
M4_FOLLOWS_CANONICAL_REALITY_ON_M3_FAILURE: YES
```

Historical Evidence may satisfy completion across an unrelated revision when
M3 reports it `CURRENT`. Completion requires an existing plan, every plan task
`SUCCEEDED`, a non-blocked/non-failed/non-cancelled run, and current M3
Evidence for every required node. Missing, stale, and unknown Evidence fail
closed. Tasks added after planning are not automatically required by that plan.

Iteration tracks accepted canonical revision advancements. Convergence checks
exact hashes in this order: `NO_STATE_PROGRESS`, `STATE_CYCLE`, then
`ITERATION_LIMIT`; the limit fails only when `iteration > max_iterations`.
Convergence failure preserves the created canonical revision and blocks the
run.

`resume_run()` fails closed and does not repair files. It verifies
manifest/run/project identity, active canonical revision/hash, task-state to
definition binding, and referenced result binding. It does not fully validate
plan content, initial manifest/state consistency, events, orphan results,
Evidence, dependency history, or iteration/hash-history consistency.

```text
RESUME_REPAIRS_FILES: NO
RESUME_INTEGRITY: IMPLEMENTED_WITH_DEVIATIONS
```

Events are immutable audit records allocated by scanning event names under the
single-threaded assumption. `state.json`, not events, is authoritative; resume
does not replay or cross-check events.

## Material Deviations

- `APPROVED_PROPOSAL_GATE: MISSING`. Despite the method name,
  `proposal.status` is never checked by M4 or M2. Historical M4 tests
  successfully apply `ProposalStatus.DRAFT` proposals.
- `PLAN_PERSISTENCE_STATUS: IMPLEMENTED_WITH_DEVIATIONS`. `plan.json` is
  overwriteable.
- `RUN_STATE_MACHINE: IMPLEMENTED_WITH_DEVIATIONS`. Lifecycle transitions are
  not centrally enforced and `RUNNING` is unused by controller flow.
- `RESULT_EVIDENCE_BINDING: PARTIAL`. Only the result binding is verified.
- `RESUME_INTEGRITY: IMPLEMENTED_WITH_DEVIATIONS`. Important bindings are
  checked, but several cross-record invariants are not.
- Test coverage directly checks a task-ID result mismatch, not every binding
  branch, and does not independently assert convergence-order precedence.
