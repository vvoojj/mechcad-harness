## Historical Role

M2 introduced the deterministic controlled mutation boundary for canonical
MechCAD state:

```text
ChangeProposal
    -> base revision/hash validation
    -> ownership validation
    -> ChangeOperation application
    -> candidate DesignState validation
    -> M1 StateManager.create_revision()
    -> new immutable canonical revision
```

M2 owns mutation authorization and validation. M1 owns canonical hashing,
revision numbering, snapshot persistence, `current.json`, and integrity
verification.

## Actual Mutation Pipeline

`ChangeEngine.apply_proposal()` historically performed:

```text
_read_current()
    -> compare base revision/hash
    -> load current state
    -> JSON-copy DesignState payload
    -> for each operation:
         ownership_policy.check()
         apply_operation()
    -> DesignState.model_validate(...)
    -> construct ChangeSet
    -> StateManager.create_revision(...)
    -> RevisionSnapshot
```

The `ChangeSet` was constructed but discarded. `apply_proposal()` returned a
`RevisionSnapshot`, not a dedicated application receipt.

## ChangeProposal and Stale Protection

Historical `ChangeProposal` fields were `revision`, `state_hash`, `id`,
`title`, `status`, `base_revision`, `base_state_hash`, `actor`, and
`operations`. Statuses were `draft`, `accepted`, and `rejected`.

There was no application status gate: all three statuses could structurally
reach the application path if other validation passed.

Compatibility validators copied `revision` and `state_hash` into
`base_revision` and `base_state_hash`, defaulted actor to `legacy`, and
defaulted operations to an empty list. This weakened the intended explicit
proposal-binding contract.

Both base revision and base hash had to match the current canonical state.
Either mismatch raised `StaleProposalError` before candidate mutation or
persistence.

```text
STALE_PROTECTION: FAIL_CLOSED
```

M2 had no project-wide lock across stale checking and revision creation;
locking is later evolution and is not attributed to M2.

## Ownership and Operations

Historical production ownership rules were:

```text
/requirements                    -> mechcad-requirements
/materials                       -> mechcad-materials
/components/*/transmission       -> mechcad-transmission
/components/*/placement          -> mechcad-packaging
```

Matching was prefix-based, using literal segments and one-segment `*`
wildcards; more literal segments were more specific. No match and wrong actor
both failed closed. The loader was a narrow line parser, not a general YAML
parser, and retained tests did not directly test the shipped configuration.

Supported operations were `add`, `replace`, and `remove`. Paths had to start
with `/`; root mutation, empty segments, and `~` were rejected. The model was
not RFC 6901: dictionary keys were literal, lists were addressed by item `id`,
and numeric list indexes and escaping were unsupported.

- `add` creates a missing dictionary field or appends a list item.
- `replace` and `remove` require an existing target.
- Operations run sequentially against one in-memory candidate.
- `expected=None` cannot express an expected-null precondition.
- List add does not verify that the path item ID equals the added payload ID.

## Atomicity and State Validation

Validation failures were semantically all-or-nothing for canonical state:
operations touched only an in-memory copy; an invalid later operation or an
invalid complete `DesignState` prevented persistence; a successful proposal
called `create_revision()` once.

The full candidate boundary was:

```python
DesignState.model_validate(payload)
```

M1 assigned the resulting revision number, so the canonical revision remained
harness-controlled.

This was not a filesystem-wide transaction. M1 writes a snapshot before
`current.json`; pointer-write failure could leave an orphan snapshot. Retained
tests cover validation failures and snapshot-write failure, not pointer-write
failure.
